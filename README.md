# `ember` — starter skeleton (Lab 1)

Copy this folder to a repository of your own, `git init`, and start from **M1** of
[Lab 01](../lab-01-a-box-of-bytes.md). It builds and runs as-is.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/ember
```

## Why a skeleton exists

Lab 1 is about **bytes and types**. It is not about `while` loops, splitting a
string into words, or `std::setw` — you meet those properly in Labs 4, 5 and 7.
So the parts that need them are given to you, fully written and commented. You
read those. You write the four small things that *are* Lab 1.

| File | What it does |

### Поломка 1: байт заворачивается

```
255 + 1 -> 0, 0 - 1 -> 255
```

Байт хранит 8 бит, то есть значения 0..255. После 255 счёт идёт по кругу: `255 + 1` даёт `0`, а `0 - 1` даёт `255`.

### Поломка 2: 0.1 + 0.2 != 0.3

```
0.1 + 0.2 == 0.3: 0, value 0.30000000000000004
```

Числа 0.1 и 0.2 нельзя точно записать в двоичной дроби, поэтому сумма чуть отличается от 0.3, а сравнение `==` даёт ложь.

### Поломка 3: строка "AB\0" в дампе

```
0000  41 42 00 0a ff 00 00 00 00 00 00 00 00 00 00 00  |AB.............|
```

Нулевой байт (`00`) в ASCII-колонке рисуется точкой, как любой непечатный байт. Поэтому по дампу не видно, что строка "AB" на нём кончилась.

### Поломка 4: память без {}

Убрал `{}` у `Byte data[MEM_SIZE]`, пересобрал и сделал `dump`:

```
0000  90 db 20 00 00 00 00 00 90 db 20 00 00 00 00 00
0010  90 db 20 00 00 00 00 00 20 00 00 00 00 00 00 00
0020  20 00 00 00 00 00 00 00 04 00 00 00 00 00 00 00
0030  07 00 00 00 04 00 00 00 98 eb 20 00 00 00 00 00
```

Без `{}` массив не обнуляется: память на стеке достаётся такой, какой её оставил предыдущий код, поэтому в дампе мусор. Чтение такой памяти — неопределённое поведение, поэтому `{}` возвращён.
## Lab 02

### Ловушка приоритета операций

```
flags & 4 == 4        -> 0
(flags & 4) == 4      -> 1
op & 0xF0 >> 4        -> 6
(op >> 4) & 0x0F      -> 1
```

При `flags = 6` (0b110) бит 2 установлен, поэтому правильный ответ 1. В C++ оператор `==` связывает сильнее, чем `&`, и `flags & 4 == 4` читается как `flags & (4 == 4)`, то есть `6 & 1 = 0`. Аналогично `>>` сильнее `&`: `op & 0xF0 >> 4` читается как `op & 0x0F`, и вместо группы (1) получается индекс (6). Поэтому в `decode()` скобки обязательны: `(op >> 4) & 0x0F`.

### Примеры ALU: перенос при сложении

Пример 1: ADD 200 + 100

```
  11001000   (200)
+ 01100100   (100)
----------
1 00101100   -> в 8 бит остаётся 00101100 = 44
```

Результат 44, Z = 0, N = 0 (старший бит 0), C = 1 (был перенос из 8-го разряда). Настоящий результат 300 не влезает в байт, поэтому он «заворачивается»: 300 - 256 = 44.

Пример 2: ADD 255 + 1

```
  11111111   (255)
+ 00000001   (1)
----------
1 00000000   -> в 8 бит остаётся 00000000 = 0
```

Результат 0, Z = 1, N = 0, C = 1. Это самый наглядный случай: Z и C стоят одновременно.

### Реализованные строки ISA

Опкод = (группа << 4) | индекс. Группа берётся как `(op >> 4) & 0x0F`.

| Опкод | Мнемоника | Что делает | Размер |
|-------|-----------|------------|--------|
| 0x00 | HALT | останавливает процессор | 1 байт |
| 0x01 | NOP | ничего не делает | 1 байт |
| 0x10 | ADD | A = A + B | 1 байт |
| 0x11 | SUB | A = A - B | 1 байт |
| 0x12 | AND | A = A & B | 1 байт |
| 0x13 | OR | A = A \| B | 1 байт |
| 0x14 | XOR | A = A ^ B | 1 байт |
| 0x15 | NOT | A = ~A | 1 байт |
| 0x16 | SHL | A = A << 1 | 1 байт |
| 0x17 | SHR | A = A >> 1 | 1 байт |
| 0x18 | INC | A = A + 1 | 1 байт |
| 0x19 | DEC | A = A - 1 | 1 байт |


Не реализованы в этой лабе: CMP, MUL и остальные группы (выполняются как NOP).

### Трассировка программы

Программа из 4 байт: `10 18 19 00` (ADD, INC, DEC, HALT). Начальные значения: A = 200, B = 100.

| Шаг | Инструкция | PC | A | B | Z | N | C |
|-----|-----------|----|---|---|---|---|---|
| 1 | ADD (A = A + B) | 1 | 44 | 100 | 0 | 0 | 1 |
| 2 | INC (A = A + 1) | 2 | 45 | 100 | 0 | 0 | 1 |
| 3 | DEC (A = A - 1) | 3 | 44 | 100 | 0 | 0 | 1 |
| 4 | HALT | 4 | 44 | 100 | 0 | 0 | 1 |

После HALT следующий `step` печатает `halted` и ничего не выполняет.

На шаге 1 сумма 300 не влезает в байт, поэтому A = 44 и C = 1. Инструкции INC и DEC флаг C не меняют, поэтому C = 1 сохраняется до конца программы.

## Lab 03

### Трассировка: ход H по данным

Данные: по адресу 0x0800 лежат байты 65 66 ('A' и 'B'). Программа из 9 байт: `28 00 08 29 02 2B 29 02 00` (LOADH H, 0x0800; LOAD A,[H]; OUT; INCH; LOAD A,[H]; OUT; HALT).

| Шаг | Инструкция | PC | A | H | Вывод |
|-----|-----------|----|---|---|-------|
| 1 | LOADH H, 0x0800 | 3 | 0 | 2048 | |
| 2 | LOAD A, [H] | 4 | 65 | 2048 | |
| 3 | OUT | 5 | 65 | 2048 | A |
| 4 | INCH | 6 | 65 | 2049 | |
| 5 | LOAD A, [H] | 7 | 66 | 2049 | |
| 6 | OUT | 8 | 66 | 2049 | B |
| 7 | HALT | 9 | 66 | 2049 | |

Флаги Z, N, C на всех шагах равны 0: инструкции группы 0x2_ и OUT их не меняют. H двигается на один байт за `INCH`, потому что ячейка памяти ember равна одному байту.

## Lab 03

### Порядок байтов: set16 и get16

16-битные значения лежат младшим байтом вперёд. Проверка:

```
set16 0 0x1234
get 0      -> 52  0x34
get 1      -> 18  0x12
get16 0    -> 4660  0x1234
```

Число 0x1234 записано как два байта: по адресу 0 лежит 0x34, по адресу 1 лежит 0x12. `get16` собирает их обратно как `lo | (hi << 8)`.

### Программа с кодом на 0x000 и данными на 0x800

Данные: по адресу 0x0800 лежит байт 65 ('A'). Программа из 5 байт: `22 00 08 02 00` (LOAD A, [0x0800]; OUT; HALT). Адрес в инструкции записан младшим байтом вперёд: 0x0800 → `00 08`.

```
set 2048 65
set 0 0x22
set 1 0x00
set 2 0x08
set 3 0x02
set 4 0x00
run
-> A
-> [3 steps]
regs -> PC=5 A=65 B=0 Z=0 N=0 C=0 H=0
```

Код живёт в регионе с 0x000, данные в регионе с 0x800, но коробка одна.

### Трассировка: ход H по данным

Данные: по адресу 0x0800 лежат байты 65 66 ('A' и 'B'). Программа из 9 байт: `28 00 08 29 02 2B 29 02 00` (LOADH H, 0x0800; LOAD A,[H]; OUT; INCH; LOAD A,[H]; OUT; HALT).

| Шаг | Инструкция | PC | A | H | Вывод |
|-----|-----------|----|---|---|-------|
| 1 | LOADH H, 0x0800 | 3 | 0 | 2048 | |
| 2 | LOAD A, [H] | 4 | 65 | 2048 | |
| 3 | OUT | 5 | 65 | 2048 | A |
| 4 | INCH | 6 | 65 | 2049 | |
| 5 | LOAD A, [H] | 7 | 66 | 2049 | |
| 6 | OUT | 8 | 66 | 2049 | B |
| 7 | HALT | 9 | 66 | 2049 | |

Флаги Z, N, C на всех шагах равны 0: инструкции группы 0x2_ и OUT их не меняют. H двигается на один байт за `INCH`, потому что ячейка памяти ember равна одному байту.

### Отчёт ASan: выход за границу массива

Отдельная пробная программа (не часть проекта) пишет на один байт за край массива из 4096 байт:

```
Memory mem;
std::size_t i = MEM_SIZE;
mem.data[i] = 1;
```

Сборка с `-fsanitize=address,undefined` даёт:

```
runtime error: index 4096 out of bounds for type 'unsigned char [4096]'
ERROR: AddressSanitizer: stack-buffer-overflow
WRITE of size 1 ... in main /tmp/oob.cpp:6
[32, 4128) 'mem' <== Memory access at offset 4128 overflows this variable
```

Важны три вещи: тип ошибки (`stack-buffer-overflow`), место (`main`, строка 6) и объект (`mem`, смещение 4128 при размере 4096). В проекте такой записи нет: `mem_set` проверяет границу и возвращает `false`, а `mem_get` возвращает 0 для адреса за пределами коробки. Поэтому команда `set 4096 1` печатает сообщение, а не портит стек.

### Вказівник хоста и адрес гостя

`CPU` хранит `Memory*` (вказівник хоста на всю коробку) и два `uint16_t`: `pc` и `h` (адреса гостя). Адрес гостя это просто индекс от 0 до 4095 в массиве `data`. Вказівник хоста это настоящий адрес в памяти компьютера (например, `0x7abc275f1020` в отчёте выше), и он меняется при каждом запуске. Если их смешать, получатся баги двух видов. Вказівник хоста не поместится в 16-битный `H` (в нём 8 байт, в `H` 2), а если и поместится обрезанным, то для программы-гостя это число ничего не значит. В другую сторону: адрес гостя, использованный как индекс без проверки, вылезает за массив, а это ровно тот случай, который поймал ASan.
